# Skills

- One skill per `skills/<name>/SKILL.md`; `name` = directory, kebab-case.
- `description` ≤200 chars: what it does + when to use, key use case first; never names a skill or subagent. Side-effect skills end with one gate clause (`Use only when the user explicitly asks to <x>[, or when chained].`). Description + `when_to_use` max 1,536.
- `SKILL.md` under 500 lines. Reference material → `references/`, link it (progressive disclosure).
- Layout (Agent Skills spec): `SKILL.md` plus only `references/` (docs Claude reads: conventions, practices, rubrics, catalogs, host rules, `commands.md`), `assets/` (content copied or filled into output: templates, files copied into target projects), `scripts/` (executables the skill runs, e.g. `build-skill/scripts/check-skill.mjs`, self-contained with `node:` imports only). No other files beside `SKILL.md`; link with `${CLAUDE_SKILL_DIR}/references/<file>`, one level deep. Every skill is standalone: no link leaves its own directory (no `${CLAUDE_SKILL_DIR}/../`), and `check-skill` runs with no `--allow`. A rule two skills need is restated, trimmed, in each; a skill reaches another skill only by chaining it through the Skill tool.
- Commands: every runnable command (git, gh, glab, package managers, CLIs) Claude runs from `## Workflow` or `## Rules` lives in `references/commands.md`, a 3-column table (`Name | Command | Purpose`, kebab-case unique names, command text exact). SKILL.md refers to it by name in backticks, with one Rules bullet "Commands: run by name from `${CLAUDE_SKILL_DIR}/references/commands.md`; never alter flags." Prohibitions (`--no-verify`, `reset --hard`, banned flags), `!`-injection lines, and `allowed-tools` stay in SKILL.md.
- Context injection: a `## Context` block of ``- Label: !`cmd 2>/dev/null || echo '<none>'` `` lines (never a bare command: a non-zero exit aborts the skill) preloads only reads that are fixed, read-only, unconditional, before any mutating step, and already covered by `allowed-tools` (root, branch, origin, tool versions). One line below it: `<none>` = read failed; a missing value or `[shell command execution disabled by policy]` = run the `commands.md` row, which stays (Purpose notes "preloaded in Context"). Not in `references/*.md` or `agents/*.md` (not preprocessed).
- Thin SKILL.md: Workflow steps are happy-path, ≤ ~2 lines (label, action by command name, the condition that branches out + link). Conditional content (conflict and retry loops with their AskUserQuestion options, failure and stop handling, host or stack variants, rationale) → `references/<topic>.md` named by topic, linked from its step; branches ≤ 2 lines and always-needed detail stay inline.
- cdk's own skills never set `disable-model-invocation`: skill chains and the end-of-task hook invoke them through the Skill tool, which the flag blocks. For other targets, `build-skill` recommends the flag only for an unchained Task skill with side effects (its `references/decide.md`); other side-effect skills gate on description (`Use only when the user explicitly asks ...`).
- Skills that chain skills, and the skills they chain, never set `context: fork`; chain via the Skill tool in the main thread, never the Agent tool, so no subagent nests another.
- Pre-approve only needed tools via `allowed-tools`. Never pre-approve `git push`, MR create/update, or comment, approve, resolve, merge endpoints; permission prompt = second guard. Never pre-approve a `glab api` or `gh api` pattern ending in `*`: flags appended after it (`-X PUT`, `-f`) turn the read into a write.
- Frontmatter order: `name`, `description`, `argument-hint`, `allowed-tools`, `disable-model-invocation`.
- Body (Task skills): `Input: $ARGUMENTS` (omit when no input), `## Rules`, `## Workflow` (numbered steps, bold labels `**Pre-flight.**`), `## Output` (fenced `text`, ends `Result: done | nothing-to-do | stopped | cancelled` + `Stopped: <step>: <reason> | none`). Reference and background-only skills use topic sections instead.
- Side-effect confirmation options name each effect ("Commit + push").
- Every loop and retry states its cap in Rules. A skill that reports findings (failed or skipped checks, gaps, open items) runs its own capped fix loop where it needs one and lists what is left under `Open:` before `Result:`. Unattended runs (chained, `--auto`, `--yes`, or invoked by the end-of-task hook) ask nothing and report what is left.
- Use `$ARGUMENTS` / `${CLAUDE_SKILL_DIR}` substitutions, not hard-coded paths.
- Known issues never live in the repo (no `SKILL.md`, no `## Known issues` section). Project-scoped ones go to Claude auto memory (`feedback` memory + `MEMORY.md` pointer).
- Verify: `plugin-dev:skill-reviewer` agent; `build-skill` drafts the skill, runs `skills/build-skill/scripts/check-skill.mjs` for the mechanical rules, scores it with `cdk:skill-scorer`, then optionally runs `skill-creator` evals (the user's choice); never run LLM-graded `claude plugin eval`.
